# App Sync

## Syno rules for this skill

- **The owner decides.** Builds and pushes happen only after a yes. Any push, tag push, store upload or workflow run needs its own yes, asked as a separate question.
- **Heavy work goes through Syno Governor.** Run builds (Tauri, Gradle, Xcode, Capacitor sync) with `gov run --label "<what>" -- '<command>'` and `run_in_background: true`, sized with `gov advise`.
- **Report in plain words.** `syno devices status` says, per platform, whether the app matches the web app; `syno devices report --confirm` saves the shared-look report. Both send a devices.parity event to Syno Pulse when it is enabled.
- **DMAIC step: Improve.**

Keep every native app a faithful, current mirror of its web application. The web app is the product and is updated directly; the desktop and mobile apps are thin native shells around it. This skill sets up and runs the mirror: it reads the project's PRD to decide how each platform tracks the web app, creates or updates the shells, moves the web build and version into them, and proves parity.

Scripts live in `${CLAUDE_PLUGIN_ROOT}/skills/devices/scripts/` (stdlib Python 3.10+). Run them with the web project root as the argument. In this file `$S` means that scripts folder.

## Standing rules (apply to everything this plugin produces)

1. **No AI attribution anywhere.** Generated code, comments, About screens, store listings, release notes, README files and commit messages never say or imply an AI or tool built the app. No "Generated by", "Built with Claude", co-author trailers, or robot emoji. The publisher is Synopus. `parity_check.py` fails the build on attribution strings.
2. **Credit footer on every screen the plugin owns** (boot, offline, update, About): "Designed & Developed by Synopus" with the company name linked to https://www.synopus.in. Use `credit` from app-sync.json.
3. **Unique, ultra-premium native chrome per app.** Never ship the baseline boot/offline pages unchanged. Read `references/premium-chrome.md` and design them for this app's brand and subject before the first release.
4. **Platforms stay separate.** Desktop and mobile live in separate folders, sync separately (`--platform`), build in separate workflows, and release on separate tags (`desktop-v*`, `android-v*`, `ios-v*`; `v*` releases all).
5. **Current, not remembered.** Toolchain and store rules change yearly. Run `check_toolchain.py` and re-verify store rules on the web before any store release (see `references/platform-baseline.md`). Never pin to versions from memory.
6. **Never commit secrets.** Keystores, certificates, API keys and updater private keys go into GitHub secrets, never the repo. Do not generate signing keys into the project folder.

## Getting the project

Work on the person's real repository. In order of preference: a linked computer folder (device tools), a GitHub repo (attach it with the add-repo tool and clone), or uploaded files. If none is available, ask which repo or folder holds the web app. Read `app-sync.json` at the repo root if it exists; it is the single source of truth.

## Workflow A — first-time setup

Use when `app-sync.json` does not exist yet.

1. **Inspect.** `python3 $S/detect_stack.py <root>`. Note framework, build command, output folder, whether the web app is bundleable (static output) or live-only (server-rendered), existing shells, PRD candidates, GitHub repo.
2. **Read the PRD.** Use the candidates from step 1, or ask for the PRD if none is found. Run `python3 $S/prd_scan.py <prd> --bundleable <true|false>` as a first pass, then read the whole PRD yourself. Decide each platform's mode with `references/prd-mode-selection.md`. The PRD is the authority; the scan is only evidence-gathering. If the PRD is silent on something decisive (offline use, native features, which stores), ask one question before deciding.
3. **Create the config.** `python3 $S/scaffold.py <root> config --name "<App>" --id <reverse.dns.id> --live-url <https://...>`. Then edit `app-sync.json`: tagline, web block (from step 1), brand colours (take them from the web app's CSS tokens or logo; never invent a palette that clashes with the product), platforms with their modes, `ota` endpoints if any platform is `bundled-ota`, `github.repo`, and the `decision` block: `source` (PRD path), `prdHash` (from prd_scan), `decidedOn`, per-platform `rationale` citing PRD sections, and `flags`. Set `versionSource` to `"web"` when the web package.json carries the release version, else `"app-sync"`. Schema: `references/architecture.md`.
4. **Design the chrome.** Restyle `app-sync/chrome/boot.html` and `offline.html` for this app per `references/premium-chrome.md`.
5. **Create the shells.** Load the `desktop-shell` skill for Windows/macOS/Linux and the `mobile-shell` skill for Android/iOS, one at a time. Each starts with `scaffold.py <root> desktop|mobile`.
6. **Sync.** `python3 $S/sync_versions.py <root> --from-web` (or plain run), then `python3 $S/sync_web.py <root> --cap-sync`.
7. **Pipelines.** Load the `release-pipeline` skill to add the GitHub Actions workflows and list the secrets to add.
8. **Prove it.** `python3 $S/parity_check.py <root> --markdown app-sync/parity.md`. Fix every FAIL. Explain each remaining WARN in plain words.
9. **Add to .gitignore:** `apps/*/www/`, `apps/desktop/src-tauri/target/`, `apps/desktop/src-tauri/gen/`, `ota-dist/`, `node_modules/`.

## Workflow B — the web app changed ("update the apps")

1. Pull the latest code. Run `detect_stack.py` again; if the framework, build command or output folder changed, update `app-sync.json`.
2. If `parity_check.py` warns that the PRD changed, re-read the changed sections and confirm the modes still hold before continuing.
3. `python3 $S/check_toolchain.py <root>`. If Capacitor, Tauri or the updater has a newer release, upgrade in the shell (see the platform skill's upgrade section). If the baseline is stale or a store release is coming, re-verify store rules on the web and write `app-sync/baseline.json`.
4. Version: `sync_versions.py --from-web` when the web app carries the version; otherwise `--bump patch|minor|major` matching the size of the change.
5. `sync_web.py --cap-sync`, then `parity_check.py`.
6. Tell the person what reaches users and when, per platform:
   - **live**: already live; nothing to ship unless the shell itself changed.
   - **bundled-ota**: the web-update workflow pushes an OTA bundle on merge to main. If parity says the native layer changed, an OTA is blocked: a store release is needed first.
   - **bundled / bundled-store**: needs a release (tag `desktop-vX.Y.Z`, `android-vX.Y.Z`, `ios-vX.Y.Z`, or `vX.Y.Z` for all).
7. If the person asks to release, hand over to `release-pipeline`. Creating tags, pushing, publishing releases and store submissions are irreversible: confirm before doing them.

## Workflow C — status check ("are the apps up to date?")

Run `parity_check.py` and `check_toolchain.py`. Answer in a few lines: which platforms match the web app, what is behind and why, and the one next action. Offer the markdown report if they want to share it.

## Script reference

| Script | Purpose |
|---|---|
| `detect_stack.py` | Framework, build, output dir, bundleability, shells, PRD candidates, repo |
| `prd_scan.py` | PRD evidence and suggested modes (`.md/.txt/.docx/.pdf`) |
| `scaffold.py` | `config`, `desktop`, `mobile`, `workflows` from templates (never overwrites without `--force`) |
| `sync_versions.py` | One version + monotonic build number across every shell (`--check`, `--bump`, `--set`, `--from-web`) |
| `sync_web.py` | Build web app, fill shells' `www/`, inject update-ready signal, `--cap-sync` per platform |
| `parity_check.py` | Versions, ids, store floors, bundle integrity, credit, attribution, PRD drift, CI (`--json`, `--markdown`, `--strict`) |
| `check_toolchain.py` | Local tools and latest published package versions vs baseline |
| `package_ota.py` | OTA bundle + manifest via Capgo CLI; refuses after native changes |
| `record_release.py` | Record a store/desktop release so OTA knows the native layer in users' hands |

`scaffold.py workflows` copies these scripts into `<root>/app-sync/tools/` so CI runs the same code. After upgrading the plugin, run it again to refresh that copy.
